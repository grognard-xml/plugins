# Grognard plugins changelog

## plugin-kanripo-import

### Heading detection for reference-folder sources

- Reference-source `.txt` files (ctext and similar folder-based witnesses) can now mark chapter/section/subsection titles so the punctuation transfer turns them into proper `<head>` elements instead of running them into the surrounding body text. Convention: an un-closed leading asterisk run — `*text` for a section, `**text` for a subsection — reusing and extending the leading-asterisk-depth style already partially in use across the ctext corpus this was built against, rather than inventing a new one. A file's very first paragraph block needs no marker at all: it's always the chapter/juan title, and (checked against the corpus's own 26 already-marked files) the first thing after it is already a section in the large majority of cases, so an unmarked block past index 0 defaults to section rather than chapter.
- A heading's own text is excluded from ordinary paragraph-to-paragraph fuzzy matching (`extract_source_paragraphs`/`_BigramIndex`) — a short, generic title like "天地名體" would otherwise false-match somewhere unrelated in a long juan. Instead each heading anchors on the _next_ paragraph in its own source file that did match something, so it's placed correctly even when its own text has no literal counterpart in the Kanripo transcription at all (routine — chapter/section titles are often dropped in transcription).
- `insert_heads` (parallel_punct.py) splices the heading in as a properly nested `<div type="chapter"|"section"|"subsection"><head>…</head>…</div>`, not a flat `<head>` sibling of `<p>` — TEI's content model only allows `<head>` _before_ any `<p>` at a given div level, so a heading landing after content has already started there needs a genuinely new nested div. Every insertion closes any currently open div at its own level or deeper before opening its own, which stays correct regardless of how many headings land in a juan or in what order, including a second "chapter"-level heading landing mid-document (each of several combined reference-source files contributes its own file-opening line) becoming a new top-level sibling div rather than an invalid second top-level `<head>`.
- The Kanripo raw source sometimes keeps a section's own label as unstamped trailing text inside the _previous_ `<p>`, with no structural separation from it. `insert_heads` now recognizes an exact match between that trailing run and the heading about to be inserted and removes it, so the label doesn't end up duplicated — once as stray plain text, once as the new `<head>`. Exact-match only, over the whole trailing run, so it never risks eating unrelated content the way a suffix match could.
- Standalone `mark_headings.py` script (ships with the ctext corpus, not the plugin) that applies this same convention heuristically to files with no existing markup: a numeral-tracking outline algorithm (validated at 96.5% against the corpus's own 26 already-marked files) that distinguishes a group header from its numbered children, plus a length cap and a sentence-punctuation gate to avoid misreading tabular/calendar content as headings. Always backs up the original before writing.

### Punctuation transfer: two silent-drop bugs

Found via systematic spot-checking of a full 121-juan Kanripo import against its ctext parallel sources, not from the unit test suite (which the first of these had already passed):

- `_slice_text_by_han_range` (used whenever a matched reference excerpt is longer than its target paragraph and gets trimmed down to size) extended the trimmed slice to include trailing punctuation after the last kept character, but never extended backward to include leading punctuation — an opening `《`/`「`/`『` immediately before the first kept character was silently dropped on every such trim rather than merely landing just outside the kept range. This was the dominant defect in the corpus: 3621 missing opening brackets/quotes across 111 of 121 files before the fix, 82 after (the residual is a different, harder problem — genuine edition variance between witnesses large enough that alignment gives up rather than guess wrong, not this bug). Fixed to pull in a leading opening mark specifically (never a trailing mark from the _excluded_ preceding content, e.g. a dropped `。` that happens to sit right before the kept range).
- `_collect_insertions`'s Han-index alignment (`_sticker_to_tape_map`, built from `difflib.SequenceMatcher`) only has entries for `equal`/`replace` opcode runs — a Han character present in one witness but not the other (a dropped duplicate, an OCR slip, an unresolved variant — routine between editions) fell in a gap with no entry at all, and a punctuation mark anchored exactly on that gap was silently discarded rather than merely landing one character off. Added a bounded nearest-neighbor fallback (`_nearest_mapped`, 6-character bridge) that walks outward to the nearest character the alignment did resolve before giving up — backward for marks that sit after a character, forward for ones that sit before one.

### Paragraph-alignment default correction

- `extract_source_paragraphs`'s "is this unmarked block a chapter continuation or the first section" default was flipped after validating both options against the corpus's 26 already-marked files: the original "unmarked and unpunctuated → chapter" default was checked against real ground truth and found correct only 2 times in 26; "unmarked past block 0 → section" is correct in the other 24. The 2-file exception (a separate work-title line and chapter-title line both before the first marked section) is an accepted, documented trade-off — there's no textual signal that distinguishes it from an ordinary first section.
