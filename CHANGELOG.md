# Grognard plugins changelog

## plugin-kanripo-import

### 0.1.2

Punctuation transfer from reference sources is substantially more accurate; the detailed write-ups of each fix follow below. In short:

- Opening brackets and quotation marks (`「『《（〔`) now attach to the character that follows them, not the one before, so they no longer land on the wrong side of a comment note, a `<seg>` boundary or a page break.
- Reference paragraphs made of many concatenated citations are matched in full instead of stopping after the first.
- Closing quotes are no longer stranded when Kanripo's ideographic-space split falls a character or two away from the reference source's sentence boundary, and a title's stray first character is reunited with its `《…》`.
- Opening brackets lost at the edge of a trimmed excerpt are restored.
- Reference files can mark chapter, section and subsection headings with a leading `*` or `**`, which become properly nested `<div><head>` structures.

### Parallel alignment: stray matches no longer stretch the matched span

- `find_han_overlap` joined every matching block between a short reference text and a long juan, so a few stray characters elsewhere in the juan (for example Wikisource licence boilerplate that matched unrelated text) stretched the matched span across thousands of unrelated characters (2,742 instead of the real 311) and applied punctuation there. Blocks are now joined only when they sit on one consistent diagonal (`MAX_DIAGONAL_DRIFT`), so the span stays on the real aligned stretch. Regression test added.

### Punctuation transfer: the paragraph after the matched text was pulled into it

- When a whole reference text (a Wikisource poem, say) matched part of a juan, the Kanripo line breaks *inside* the matched text were reflowed into one paragraph, but so was the break right after its last character, so the next paragraph (the following poem's title, `巫咸山賦<note>有序</note>`) ended up inside the stamped paragraph, as if it belonged at its end. That boundary break is now kept for single-tape (whole-text) matches. Per-paragraph matching still drops it on purpose, since there it is what rejoins one citation that Kanripo split across two `<p>`s. Regression test added.

### Parallel alignment: variant characters no longer count against the match

- Locating a reference text in a juan now compares on a length-preserving variant fold (the DPM variant table plus the 1:1 entries of the hard-replacements table), so 於/于, 兹/茲, 棋/棊, 濳/潛 and similar equivalents no longer count as mismatches against the 80% coverage threshold. The fold is for comparison only: indices are unchanged and the Kanripo text itself is never altered.

### Punctuation transfer: reference title inside a `<head>` made the whole transfer fail silently

- A reference text that opens with its own title (Wikisource pages do: `蜜蜂賦`, then the poem) matched the `<head>` of the same name in the file, and the paragraph-break step then emitted `</p><p>` *inside* the `<head>` (`<head><seg>蜜蜂賦</seg></p><p></head>`). The result was not well-formed, so the transfer failed closed and reported "no match" for a text that did align. Paragraph breaks are no longer inserted inside a `<head>`, and the stamp is closed at `</head>`. Regression test added.

### Heading detection for reference-folder sources

- Reference-source `.txt` files (ctext and similar folder-based witnesses) can now mark chapter/section/subsection titles so the punctuation transfer turns them into proper `<head>` elements instead of running them into the surrounding body text. Convention: an un-closed leading asterisk run — `*text` for a section, `**text` for a subsection — reusing and extending the leading-asterisk-depth style already partially in use across the ctext corpus this was built against, rather than inventing a new one. A file's very first paragraph block needs no marker at all: it's always the chapter/juan title, and (checked against the corpus's own 26 already-marked files) the first thing after it is already a section in the large majority of cases, so an unmarked block past index 0 defaults to section rather than chapter.
- A heading's own text is excluded from ordinary paragraph-to-paragraph fuzzy matching (`extract_source_paragraphs`/`_BigramIndex`) — a short, generic title like "天地名體" would otherwise false-match somewhere unrelated in a long juan. Instead each heading anchors on the _next_ paragraph in its own source file that did match something, so it's placed correctly even when its own text has no literal counterpart in the Kanripo transcription at all (routine — chapter/section titles are often dropped in transcription).
- `insert_heads` (parallel_punct.py) splices the heading in as a properly nested `<div type="chapter"|"section"|"subsection"><head>…</head>…</div>`, not a flat `<head>` sibling of `<p>` — TEI's content model only allows `<head>` _before_ any `<p>` at a given div level, so a heading landing after content has already started there needs a genuinely new nested div. Every insertion closes any currently open div at its own level or deeper before opening its own, which stays correct regardless of how many headings land in a juan or in what order, including a second "chapter"-level heading landing mid-document (each of several combined reference-source files contributes its own file-opening line) becoming a new top-level sibling div rather than an invalid second top-level `<head>`.
- The Kanripo raw source sometimes keeps a section's own label as unstamped trailing text inside the _previous_ `<p>`, with no structural separation from it. `insert_heads` now recognizes an exact match between that trailing run and the heading about to be inserted and removes it, so the label doesn't end up duplicated — once as stray plain text, once as the new `<head>`. Exact-match only, over the whole trailing run, so it never risks eating unrelated content the way a suffix match could.
- Fixed a heading landing in the wrong juan entirely: a whole-work import pools every reference file against every juan in one `align_paragraphs` call, and this genre's heavily formulaic phrasing (near-identical boilerplate across structurally similar star/omen entries) means one of an unrelated file's ordinary paragraphs can out-score the correct file's own on pure text similarity. Real case: the table-of-contents juan picked up chapter headings from ~30 unrelated files; an ordinary juan picked up a heading from a completely different star's section. `align_paragraphs` itself is deliberately left unrestricted — a cross-juan match there only ever decorates the target's own already-present Han characters with punctuation, never adds text, and borrowing punctuation for a genuinely repeated sentence from wherever it's found is correct. The actual risk is narrower: `_resolve_heading_insertions` inserts a heading's own text verbatim as new `<head>` content, and that's gated specifically — a match only counts as a heading anchor when the source file's own number (`03.txt`) corresponds to the target juan's own number (parsed from `<pb n="KR..._003-...">`), falling back to unrestricted only when either side has no parseable number (non-numeric filenames behave exactly as before). An earlier version of this fix restricted `align_paragraphs` itself, which was a stricter trade-off than necessary — it blocked legitimate cross-juan punctuation sharing to prevent a problem that only ever occurs at the heading-insertion step.
- That gate silently never engaged at all against real imports: the Kanripo plugin's own `meta.juan` (what `RefParagraph.juan_id` actually gets built from) is a human-readable locator like `"卷三"`, never the bare digits `_numeric_juan_key` was parsing for — `kanripo_tei.py` prefers the source's own header-embedded locator over the clean integer its pb markers also carry whenever that header field is present, which is effectively always. `_numeric_juan_key` now also parses a `"卷<Han numeral>"` locator (`"卷三"` -> 3, up to `"卷一百二十"` -> 120) and recognizes a handful of front-matter labels (`目錄`/`目次`/`序`/`前言`/`凡例`) as juan 0, matching Kanripo's own pb-marker convention of numbering front matter before juan 1 (confirmed directly: this corpus's table-of-contents juan's pb markers read `KR..._000-...`). Tests for the previous version of this gate used simplified plain-digit `juan_id`s that happened not to exercise this gap at all; added one using the real locator format specifically.
- Standalone `mark_headings.py` script (ships with the ctext corpus, not the plugin) that applies this same convention heuristically to files with no existing markup: a numeral-tracking outline algorithm (validated at 96.5% against the corpus's own 26 already-marked files) that distinguishes a group header from its numbered children, plus a length cap and a sentence-punctuation gate to avoid misreading tabular/calendar content as headings. Always backs up the original before writing.

### Punctuation transfer: two silent-drop bugs

Found via systematic spot-checking of a full 121-juan Kanripo import against its ctext parallel sources, not from the unit test suite (which the first of these had already passed):

- `_slice_text_by_han_range` (used whenever a matched reference excerpt is longer than its target paragraph and gets trimmed down to size) extended the trimmed slice to include trailing punctuation after the last kept character, but never extended backward to include leading punctuation — an opening `《`/`「`/`『` immediately before the first kept character was silently dropped on every such trim rather than merely landing just outside the kept range. This was the dominant defect in the corpus: 3621 missing opening brackets/quotes across 111 of 121 files before the fix, 82 after (the residual is a different, harder problem — genuine edition variance between witnesses large enough that alignment gives up rather than guess wrong, not this bug). Fixed to pull in a leading opening mark specifically (never a trailing mark from the _excluded_ preceding content, e.g. a dropped `。` that happens to sit right before the kept range).
- `_collect_insertions`'s Han-index alignment (`_sticker_to_tape_map`, built from `difflib.SequenceMatcher`) only has entries for `equal`/`replace` opcode runs — a Han character present in one witness but not the other (a dropped duplicate, an OCR slip, an unresolved variant — routine between editions) fell in a gap with no entry at all, and a punctuation mark anchored exactly on that gap was silently discarded rather than merely landing one character off. Added a bounded nearest-neighbor fallback (`_nearest_mapped`, 6-character bridge) that walks outward to the nearest character the alignment did resolve before giving up — backward for marks that sit after a character, forward for ones that sit before one.

### Concatenated-citation punctuation loss

Found by spot-checking a *correctly-reimported* juan after the two fixes above — the heading/bracket fixes were confirmed working, but closing `」` quotation marks were still missing at a striking rate (44 to 192 per file in an 8-file sample). Root cause was two compounding bugs, both in the same area:

- `split_paragraphs`'s sentence-splitting regex (`_SENTENCE_SPLIT_RE`) split reference text right after every `。！？`, with no regard for a closing quote/bracket immediately following it (`"...二年。」郗萌曰..."`, extremely common — a quoted citation's sentence ends *inside* the quote). The closing mark was stranded as the *next* unit's leading character, sometimes becoming its own isolated unit containing nothing else. Fixed to keep up to two stacked closing marks (`」』》）〕`) attached to the sentence they close.
- Separately: Kanripo `<p>` breaks are page-line based, and when a `<p>` concatenates two whole citations with no separator between them (Kanripo's own citation-boundary convention, an ideographic space, isn't guaranteed present), `align_paragraphs` would find the first citation's own source paragraph as a *perfect* containment match (score 1.0 — wholly, correctly found inside the combined ref key) and stop there, never attempting the existing merge-neighbors fallback, which only ever triggered on a sub-threshold score. A perfect score says nothing about whether the ref key has more content *after* the match that was left uncovered. `align_paragraphs` now also attempts the merge search whenever the single candidate accounts for under 90% of the ref key's own length, keeping the single match if no wider-coverage merge is found so an already-complete match is never needlessly widened.

Both root-caused and fixed from one real example (`KR3g0018_090`, `石氏曰：「彗星出攝提...」` losing its `」` while the next citation, `郗萌曰：「...」`, lost all of its punctuation outright) traced step by step through the actual pipeline functions against the real ctext source text, not guessed at from the symptom.

### Paragraph-alignment default correction

- `extract_source_paragraphs`'s "is this unmarked block a chapter continuation or the first section" default was flipped after validating both options against the corpus's 26 already-marked files: the original "unmarked and unpunctuated → chapter" default was checked against real ground truth and found correct only 2 times in 26; "unmarked past block 0 → section" is correct in the other 24. The 2-file exception (a separate work-title line and chapter-title line both before the first marked section) is an accepted, documented trade-off — there's no textual signal that distinguishes it from an ordinary first section.

### Merge-window search: the real generalizable fix behind the symptoms above

Found by tracing a specific, real duplicated-quote example (`KR3g0018_014`'s `《帝覽嬉》曰：「月入太微而出端門者，臣不臣。」` losing its own opening `「` into a duplicate while an unrelated neighboring citation got its text blended in) all the way back through `align_paragraphs`, not by pattern-matching the symptom:

- `align_paragraphs`'s "retry with neighboring source paragraphs" fallback only ever triggered when the single best candidate's score fell *below* `similarity_threshold`. A Kanripo `<p>` concatenating several whole citations with no separator (routine — found for real, up to 135 consecutive `<seg>` stamps in one `<p>`) makes the *first* citation's own source paragraph a **perfect** containment match (1.0 — correctly, wholly found, in order) that still only covers a fraction of the `<p>`'s full content; a perfect score never triggered the fallback, so everything after that first citation went unmatched or got silently blended with whatever came next. `align_paragraphs` now also retries whenever the single candidate accounts for under 90% of the ref paragraph's own length, regardless of its score.
- The retry itself (`_grow_merge_window`, replacing the old fixed-size, O(window²) brute-force search entirely) is now a greedy, linear-time growth: extend the window by one source paragraph at a time, backward or forward, on whichever side still covers more of the ref paragraph (`_coverage_count` — stable even once the merged window grows past the ref paragraph's own length, unlike a plain ratio or raw length, both of which keep climbing from added bulk alone and so can't actually tell "still helping" from "just getting bigger"). `DEFAULT_MAX_MERGE_WINDOW` raised from 3 to 200 accordingly — cheap now that growth is linear, where it would have been an unworkable O(200²) search before.
- Growth tolerates up to 3 consecutive non-improving steps (`_MERGE_GROWTH_PATIENCE`) before giving up a direction, reverting to the best window actually found rather than wherever patience ran out: one paragraph along a long run whose wording has drifted from this witness (ordinary edition variance, not a bug) adds nothing to coverage on its own, but the paragraph after it usually resumes covering real content — stopping at the first flat step would silently truncate an otherwise-correct long run right at that one paragraph.
- This is very likely the single highest-impact fix in this whole investigation: every other punctuation-transfer bug found and fixed this session affected one mark at a time, but a `<p>` with no internal separator and an undersized merge window previously meant *everything past the first citation* in that `<p>` went unmatched or corrupted, not just one mark.

### Doubled opening quote/bracket mark across adjacent `<seg>`s

Found by widening the same spot-check from "literal character doubling" (`([「《『])\1` against raw text, which found only 1 real instance) to "doubling once tags are stripped" (485 occurrences across 91 of 121 files) -- the visual `「「` a reader sees is almost never two literally adjacent characters in the raw XML; it's one mark trailing a `</seg>` immediately followed by the same mark leading the next `<seg>`.

- Root cause: the Kanripo raw text sometimes splits what is really one citation into two separate ref paragraphs right at the seam between an attribution and its quoted content (`"京氏曰"` | `"日出于夕..."`), each matched independently against the source. The first paragraph correctly attaches the source's `：「` as its own trailing ("after") mark; the second, matched on its own, finds that same `「` sitting immediately before its own first Han character in the source and re-attaches it as its own leading ("before") mark. Each insertion is individually correct -- `align_paragraphs` has no visibility into what a *different* ref paragraph's match already claimed -- the duplication exists only across the pair, which is why the existing single-match insertion logic could never have caught it.
- Fixed with a finalization pass (`_dedupe_seg_boundary_marks` in parallel_punct.py, run once over the fully-assembled juan after all paragraph-scoped matches are applied) that collapses a run of 1-2 opening marks (`「『《（〔`) landing identically on both sides of a `<seg>` boundary, keeping the first (closing/attribution side) copy and dropping the second (opening/content side) one.
- Verified against the real case this was traced from (`KR3g0018_006`, `京氏曰：「日出于夕，人君不祥，社稷亡。」`) and confirmed the source text itself has only one `「` at that seam, not two -- this is not a pre-existing ctext transcription error like the `90.txt` case earlier in this investigation, it's a genuine alignment-pipeline duplication.
- Superseded below by a fix to the actual root cause this was papering over -- kept as a harmless no-op safety net rather than removed, since nothing in the pipeline guarantees no other path can still produce a literal duplicate.

### The real root cause: every mark glued to the *preceding* character, even opening ones

A second, wider spot-check surfaced three more symptoms that all looked unrelated on the surface -- a stray `《` landing mid-word (`《黃帝》曰` becoming `《曰` with `黃帝` silently eaten), a word split by a stray comma+period (`赦不從` becoming `赦不，。」從`), and a title bracket stranded *inside* the comm note that happened to precede it (`《河圖》` becoming `河圖》` with the `《` left behind inside `</note>`, silently losing itself as a trailing mark on the note's own last character). Tracing each one back (not pattern-matching the symptom) found they were all downstream of the same single root cause in `_collect_insertions`:

- Every punctuation character copied from a parallel witness was unconditionally attached as a *trailing* mark on whichever Han character came immediately before it -- including opening marks (`「『《（〔`), which semantically belong to whatever comes *after* them, not before. This is invisible the vast majority of the time, because the preceding and following Han characters are usually both inside the same stamped span, so which side the mark nominally "belongs" to makes no visible difference. It only surfaces as a bug whenever some structural boundary -- a comm note closing, two independently-matched ref paragraphs, an ideographic-space split landing one character off from where the source naturally splits -- falls between those two characters, because then the mark renders on the wrong side of that boundary: inside a note it doesn't belong to, attached to a word fragment it doesn't belong to, or (combined with the `_trim_source_text_to_target` gap above) glued onto an untrimmed prefix that didn't belong to this match's text at all.
- Fixed by making an opening mark always buffer forward for the next Han character, the same way a mark seen before any Han at all was already buffered (that existing case -- `《title》` opening a reference text -- was in fact the *same* bug, just at a boundary coincidentally already handled: the very start of the parallel text).
- This isn't a separate, narrower fix alongside the ones above -- it's the actual mechanism behind all of them, and resolves every real-corpus example gathered from this investigation (the title-prefix case, the mid-word split, and the note-boundary case) with a four-line change to a single function, rather than patching each boundary kind separately.

### Last gap in the same family: a merge-retry threshold with a blind spot for punctuation

A full-corpus bracket-balance scan after the fix above (0 doubled marks corpus-wide, confirming that bug is gone) still found ~400 opening brackets missing across 104 of 121 files -- all one shape: a title's `《` stranded at the very end of the *previous* citation, consistently one Han character short. Root cause: `align_paragraphs`'s merge-retry only fires when a single candidate's coverage falls under 90% of the ref paragraph's own key length, and that 90% margin was deliberately loose (see the removed `_MIN_SINGLE_CANDIDATE_COVERAGE`) to avoid re-triggering merges on a single citation's own ordinary sentence-initial padding. But coverage is measured in Han characters, and an opening bracket isn't one -- so a ref paragraph missing only its trailing title-opening `《` (and the first Han character after it, which belongs to the *next* citation's own text in Kanripo's own split) can sit at 94% coverage, comfortably over the 90% bar, and never retry at all even though the one character it's missing is exactly the one carrying the stranded mark.

Fixed by retrying on *any* shortfall, not just one past the 90% margin: `_grow_merge_window` only ever replaces a single match when growing genuinely improves coverage (unchanged safeguard from the original merge-window fix), so retrying more often costs a little extra search time on an already-correct short match and changes nothing about its result -- it only matters on the real gap. `_MIN_SINGLE_CANDIDATE_COVERAGE` is now unused and removed.

### Two more ideographic-space edge cases (stranded closing marks)

Found by reading an 8- and 12-juan sample after the previous round; the remaining defects were all closing `。」` marks lost where Kanripo's ideographic-space split lands a character or two away from the ctext sentence boundary:

- The merge-retry's "is the single candidate short?" test compared key *lengths*. When the chosen source paragraph is longer than the ref (it also holds the next citation's tail) the test passed even though the ref's first character (`年` of `…不出三年。」《高宗占》`) lived in the previous source paragraph, so that paragraph's `。」` was never reached. It is now an in-order coverage count (`_coverage_count`), the same measure `_grow_merge_window` uses.
- A one-character ref paragraph (`死` of `…太子死。」`) is too short to match anything and was left unstamped, dropping the `。」` after it. `apply_paragraph_scoped_sources` now folds an unmatched orphan of up to four Han characters into the preceding match's scope, but only when the source text that match already covers actually ends with those characters; otherwise it is left alone.
- Mirror of the orphan fold above: a title's *first* character left alone at the end of the previous `<p>` (`洪` of `《洪範傳》`, `孝` of `《孝經雌雄圖》`) is claimed by the following match instead, when that match's source text begins with it. Found as the dominant residual in a corpus-wide scan (stray closing `》` with no opener); each one was a stranded title initial, not a matching error.
